# 大数据与波形交互压力测试（2026-10-26）

## 结论

本机实测：256 通道、每通道 2000 Hz、满 60 秒历史缓存的持续采集，在真实窗口中同时进行时间缩放、平移、Y 轴缩放和取消 CSV 导出，运行 300 秒成功，最终错误数为 0。缓存经历约 5 次完整覆盖，没有出现缓存随运行时长无界增长。

高通道全历史视图仍有明显绘图成本，不能把通过压力测试理解为任意规模都能达到 60 FPS，也不能把 512 MiB 缓存预算理解为整个进程只有 512 MiB。

## 环境与方法

- Windows 11，AMD Ryzen 9 7945HX3D（16 核 / 32 线程），约 96 GB 内存。
- .NET SDK 10.0.401，运行时 .NET 10.0.12，Avalonia 12.1.4，Release。
- 所有通道均可见；测试数据包含连续波形和正负尖峰。
- 历史测试预填充缓存到上限，然后在 1 / 4 窗格中通过真实输入处理函数缩放、平移并调用真实 Skia 离屏绘图，每种情况记录 120 帧。单窗格为 900×500，四窗格每个 900×180 逻辑像素。
- 实时测试在独立新进程中打开现有 `MainWindow`，预填充满历史后，再真实计时采集 300 秒，避免历史测试遗留分配影响实时内存趋势。每约 50 ms 发出交互，期间执行一次一致性 CSV 快照并取消导出。
- 输入坐标经过视觉根转换，并验证缩放确实生效；并非只调用 `InvalidateVisual()` 或仅测数组查询。
- UI 布局、资源文案与图标的文件 SHA256 在测试前后保持一致；未修改既有布局、控件、字体、配色和文案。

## 满历史绘图结果

P95 表示本次样本中 95% 的耗时不超过该值。表中为离屏完整绘图耗时，不是桌面显示的实际 FPS。

| 通道 | 总缓存点数 | 每通道历史 | 单窗格绘图 P50 / P95 | 四窗格合计绘图 P50 / P95 | 四窗格交互处理 P95 |
|---:|---:|---:|---:|---:|---:|
| 32 | 3,840,000 | 60 s | 8.48 / 27.17 ms | 5.95 / 24.81 ms | 0.26 ms |
| 128 | 15,360,000 | 60 s | 15.28 / 89.55 ms | 15.39 / 83.15 ms | 0.28 ms |
| 256 | 30,720,000 | 60 s | 28.78 / 124.77 ms | 26.16 / 126.86 ms | 0.87 ms |
| 512 | 31,580,160 | 30.84 s | 35.98 / 135.90 ms | 31.87 / 142.43 ms | 1.51 ms |

512 通道时，内存预算自动将每通道容量降为 61,680 点。表明压力增加时通过缩短历史约束缓存，而不是持续扩充数组。

同类基线场景中，256 通道四窗格 P95 约 253 ms，优化后约 127 ms；缩放/悬停相关数据处理从十几至几十毫秒下降至约 1 ms。不同采样长度和系统负载会影响对比数值。

## 300 秒真实窗口结果

- 256 通道，请求每通道 2000 Hz，实测平均 **2000.01 Hz**。
- 完成 **600,051 帧**，约 **153,613,056 个通道样本**。
- 自动交互 **5,640 次**，时间轴和手动 Y 轴始终保持有效有限范围。
- 交互处理 P50 / P95 / 最大：**0.028 / 0.096 / 7.811 ms**。
- 20 ms UI 心跳间隔 P50 / P95 / 最大：**29.14 / 47.65 / 572.93 ms**。这是 UI 线程调度延迟指标，不等于鼠标端到端响应时间。
- 采集最大读间隙约 **103.06 ms**。平均 2000 Hz 不代表每个采样间隔恒定，快照、GC 和调度仍会造成抖动。
- CPU 约为 **1.12 个逻辑核等效用量**，不是整机 112%。
- 托管分配约 **7.17 MiB/s**；未处理异常、采集错误和导出文件保护错误均为 0。

内存观察：

- 单独的满缓存历史数据及相关托管对象：256 通道约 497 MiB，512 通道约 511 MiB。
- 256 通道一致性快照期间托管内存约 1 GiB，符合增加一份历史副本的预期。
- 300 秒实时场景预热后，进程私有内存大体在 **2.7–3.1 GiB** 范围波动；包括 CLR 保留空间、原生绘图、UI、缓存和临时快照。
- 结束后诊断性 GC 的托管存活量约 **589 MiB**；进程私有内存仍约 **2.9 GiB**。原生/运行时保留内存并不会立即归还系统，不能以托管存活量代替进程占用。
- 后半程没有按采样写入总量线性上涨的趋势，但 5 分钟不能证明不存在更长时间或其他操作路径的泄漏。

## 压测发现并修复的问题

1. 绘图区宽度极小时，时间刻度的 `Math.Clamp` 上下限颠倒，导致绘图异常。现已增加最小可绘制区域检查和安全夹取。
2. 零垂直滚轮增量也会缩放，现已忽略；鼠标捕获丢失时清理拖拽状态。
3. 自动 Y 轴和悬停重复抽取整窗数据。现使用缓存分块摘要计算范围，并直接二分查找最近原始采样点。
4. 多条交叉曲线合并到同色巨大路径中，增加原生描边成本。现保持颜色绘制顺序，但各曲线使用独立路径。
5. 增加线性、无额外逐帧分配的屏幕空间简化，误差不超过 0.25 个逻辑像素；原始样本、统计、CSV 和光标取值保持独立，不被简化修改。
6. 处理 NaN/Infinity 和极端有限数值，避免向原生绘图传递非有限坐标。
7. 解除脱离视觉树的图表事件订阅，并对文字测量缓存设置固定容量。
8. 大快照不再阻塞 UI 读取显示用采集指标；环形缓存导出复制改为两个连续区段，避免逐点取模。

压测中曾尝试复用已发布的可变 `StreamGeometry`，该实验触发原生访问异常，已完全撤回。最终实现每帧构造新路径，发布后不再修改，随后完成了上述 300 秒完整回归。后续优化应保持这一并发约束。
